# 渐进式 TODO 树

这个 Skill 只帮助规划、判断和维护状态，不执行 TODO 中的实际任务。它提供一组判断方向，不把 Agent 锁进固定的评分器、审计账本或强制流程。遇到具体任务时，结合用户意图、已有规则和当前证据取舍；只有对结果有帮助时才展开、升旗或更新状态。

除持久化事实、诚实报告和不执行 TODO 实际任务等边界外，下面的路线规则都更像思考提示，而不是必须逐字执行的流程。可以偏离某条建议，但最好说明当前情境为什么不适用。

## 先找权威状态

如果用户给了 `TODO.md` 路径，先读它；否则优先使用当前任务目录的 `TODO.md`。如果这两个位置都找不到本地 `TODO.md`，先根据当前话题在用户可写的位置创建一个简短、可辨识的文件夹，再在其中创建 `TODO.md` 并作为权威状态。文件夹名应使用话题本身；位置或话题不明确时，向用户确认，不要擅自使用过宽或无意义的名称。

只有本地路径不可写或用户明确要求使用 Notion 时，才使用用户提供的 Notion 页面或数据库。写入前先读取实际结构，搜索已有同主题页面并局部更新，不要为一次状态变化新建重复页面。用户没有提供目标位置时先确认；写入失败时如实说明，不要假称已经保存。

持久化内容是接管依据，聊天是思考区。另一个 Agent 只读最近的完整状态和其后的正式变更，应能大致继续；不要靠长会话记忆重建整棵树。

## 新增 TODO 的定位

当前目录已有权威 `TODO.md` 时，用户说“另起一个 TODO”“插一个 TODO”或“先解决这个 TODO”，默认是在现有树中新增节点，不新建文件或文件夹。只有用户明确要求独立项目／独立文件，或新问题与现有根目标没有依赖关系时，才创建新的权威 TODO。

新增节点前，先判断：“这个任务服务于哪一个现有节点，完成后推进什么？”服务于某阶段、准备、验证或收口的事项，挂在该节点下；只有本身是独立长期目标，才放在顶层。若有两个同样合理的父节点，再向用户确认；否则直接放到最近的正确父节点。

## 从第一性原理重建当前问题

当任务开始进入路线或方案、现有做法被默认为唯一办法、预算压缩找不到真正的核心结果，或连续工作只是在优化旧方案时，先退回当前可确认的事实重新推导。规格明确、便宜且可逆的例行工作不必机械重做这一层。

- 先用不包含现有方案名称的语言说明要得到的可观察结果：“如果这个方案从未存在，最后仍必须发生什么变化？”
- 区分已经由当前证据支持的事实、不能违背的硬约束，以及尚未验证的假设、习惯和实现偏好。当前方案只有在能由前两者推出时才是必要条件，否则只是候选路线。
- 从结果、事实和硬约束直接推出最小下一步，不默认修补或延长旧方案。过去的工作可以保留为证据和历史，但不能仅因已经投入过就获得优先权。
- 不把“第一性原理”当作清空知识的口号。适用的专业知识、用户已确认的价值选择、法律、安全边界和当前观察都应保留；只有其适用性受到新证据挑战时才重新打开。
- 能通过读取现场或验证事实解决的问题由 Agent 直接查清；若剩下的是互相冲突的价值目标，只向用户提出一个会改变路线的具体取舍。

可以用下面的短状态暴露推导，不必为每个节点建立假设账本：

```text
要得到的结果：不借用现有方案描述最终变化。
事实与硬约束：当前证据支持什么，什么不能违背。
暂定假设：哪些判断仍可能是错的。
从头推导的最小下一步：现在为什么只做这一步。
反证：出现什么信息时，这次推导需要重来。
```

第一性原理负责判断“真正要保住什么、当前方案是否必要”，预算压缩负责判断“最少投入多少能保住它”。如果重新推导后发现当前方案并非必要，不要继续压缩旧方案的预算，应先回到根路线复审。

## 在明显投入前压缩预算

当一条路线可能耗费明显的金钱、时间、注意力、开发量、样本量或协作成本，而完整做法还没有被证明必要时，先用受限预算寻找保住核心结果的最小行动，不要让富裕预算自然长成完整方案。便宜、可逆且规格明确的工作不必机械套用；安全、合规、数据完整性等不能压缩的底线应直接说明。

- 先说清完整投入真正要买到的核心结果，区分不可替代的体验或决策证据，与实现手段、完整度和便利性。
- 把完整预算暂记为 `1000`，再分别只批 `100` 和 `10`，检查每一档能否保住接近的核心结果。数字只是相对刻度，也可以换成当前任务更自然的预算单位。
- 每一档只需说明：保住什么、最小行动是什么、删掉或推迟什么、会损失什么，以及是否仍足以支持当前决定。不要用功能数量、任务完成率或表面相似代替核心效果。
- 如果低预算方案已经换了问题、无法产生同一种关键证据，或核心体验明显失真，就如实判定“不等价”，并指出不能再压缩的最小成本，不要把缩水结果包装成差不多。
- 默认选择足以支持当前决定的最低一档作为当前节点；更高预算只保留为粗粒度的待后续，并写明什么新证据才允许追加投入，不把完整方案提前当成已经获批。
- 能唯一判断的例行删减由 Agent 直接完成；若有多个互相冲突的核心结果，或必须由用户决定牺牲哪个价值，只提出一个高信息密度的具体问题。

可以用下面的短状态承载这次判断，不必发展成逐节点评分表：

```text
核心结果：预算再低也不能失去什么。
预算压缩：1000 / 100 / 10 各自保留什么、损失什么。
当前批复：先做哪一档，以及为什么足以支持当前决定。
追加条件：出现什么证据后，才值得释放下一档预算。
```

如果压缩后发现低预算行动只能验证局部可行性，却回答不了原路线是否值得投入，应回到根路线复审，而不是继续把同一路线切成更多廉价变体。

## 让树保持可用

可以把下面这些当作默认倾向，并按当前情境调整：

- 顶部展示一棵纯 TODO 树，只放任务框、层级和任务名称，不放结论、上下文或解释。其后可以保留一棵供 Agent 接管的详细工作树、当前状态和少量关键上下文；两棵树的节点与完成状态保持同步。
- 节点不使用顺序编号。通常用任务名称和层级定位，避免 Notion 对编号清单的渲染干扰。
- 一次主要服务于一个当前节点。发现不阻塞当前节点的问题，可以先放入“待后续”，不必立即切换。
- 越近的工作越具体，越远的工作越粗。能由已有规则唯一推出的边界，不必另长节点。
- 正式推进过的判断路径通常保留，即使后来暂停或换根；局部结论放在对应节点，不要把关键上下文变成第二棵树。
- 只把用户确认、外部证据或已经确定的结构变化写成正式状态。把“暂定采用”和“已经验证”分开写。

推荐的工作区结构如下，展示树和工作树都可按需要压缩：

```markdown
# TODO

- [x] 区分问题来源
  - [x] 还原关键事实
- [ ] 设计最小机制
  - [ ] 当前节点
- [ ] 后续验证

## Agent 工作树（接管用）

这里保留必要的节点结论、当前状态、关键上下文和待后续。
```

## 关闭顶层分支时压缩归档

当根节点下面的一层分支被正式关闭时，尝试马上压缩归档。关闭包括已完成、经确认暂停/放弃，或被正式换根替代；若分支仍有可执行的后代、仍是当前路线，或其中的信息会直接阻塞其他活跃分支，就不要归档。

- 先抽取仍对当前工作有用的最小信息：已确认的结论、未完成但需要转交给其他分支的事项、跨分支约束，以及恢复该分支所需的一句触发条件。把这些内容移入当前工作树或对应的活跃节点，不要依赖历史文件来维持进行中的工作。
- 将关闭分支的详细工作树、证据和判断路径移到权威状态旁的 `archive/` 中，一条顶层分支一个 Markdown 文件；文件名使用关闭日期和简短分支名。Notion 中则移到单独的历史子页面或归档区。归档保留“为什么这样结束”的必要依据，但不复制仍有效的当前状态。
- 在 `TODO.md` 保留一个简短的“历史索引”，每项只写分支名、关闭状态、核心结论或停止原因、归档位置，以及需要恢复时的触发条件。展示树只保留该顶层节点的关闭状态和名称，不放长历史。
- 压缩后检查活跃树是否仍可独立接管：另一个 Agent 不打开归档，也应知道当前目标、当前节点、下一步和跨分支约束。若做不到，先补足当前状态再归档。
- 后续若需要恢复某分支，先从索引定位并读取对应归档，再把恢复所需的最小节点和上下文带回工作树；不要把整段历史原样搬回。

可采用如下形态：

```markdown
## 历史索引

- 已完成｜区分问题来源：确认问题在接口边界；归档：`archive/2026-08-11-区分问题来源.md`；仅当接口约束变化时恢复。
- 已暂停｜旧验证路线：样本不足以判断价值；归档：`archive/2026-08-11-旧验证路线.md`；获得代表性样本后复审。
```

## 保持根路线可被重新审视

当任务从“事实/经验”走向“路线/方案”时，可以用两行短状态帮助当前判断：

```text
当前路线假设：因为 X，所以先走 Y，预期带来 Z。
重审条件：出现什么信息时，需要暂停并重新判断。
```

只在路线确定、关键前提变化、暂停、恢复或换根时更新，不必为每个节点维护假设。

对根目标、约束、路线和关键前提保持主动怀疑。重点不是反复争论，而是看新信息是否已经让原路线失去必要前提，或连续的局部处理仍然无法进入产品价值判断。

可把以下信号当作参考，而不是硬阈值：

- 单一新事实直接挑战路线的必要前提，并能提出不改目标和成功标准的反证问题。
- 一次局部失败可以正常修复；独立尝试仍无法进入路线价值判断时，路线张力开始累积；继续增加变体前值得升旗复审。
- 后续工作只是在修复可检验性、解释失败或不断缩窄结论，却仍回答不了整条路线是否值得投入。

单次工具、样本、环境或协议故障，如果修复后仍能直接判断原路线，通常只是局部问题，不必上升为路线危机。

升旗更像是提醒暂停扩张和共同复审，而不是自动换根。Agent 可以先说明当前路线、触发证据、直接反证问题和建议；涉及修改根目标、继续投入仍无法判断价值的路线、正式暂停/退出/换根，或明显改变成本、风险和范围的方向时，保留用户的最终选择。

## 区分探索和路线

一个实用的反事实问题是：

> 如果这个候选想法是错的，我们还会不会做同样的下一步？

若仍然会做，通常只是收集信息或比较方向；若不会做，下一步已经依赖这个候选，通常适合把它公开写成当前路线假设并接受根路线复审。这样可以避免正常探索被过早打断，也避免把已经实际押注的路线伪装成“只是探索”。

## 暂停、保留和恢复

如果路线升旗后仍没有足够理由恢复，通常可以选择明确暂停：

- 旧路线和暂停理由留在历史树中，作为“为什么走过、为什么停下”的记录。
- 当前状态可以明确写成“暂无当前路线”，尽量不要用旧路线或模糊方向补位。
- 通常不给旧路线保留“最后再试一个小实验”的默认续命通道；其他不依赖旧路线的信息收集仍可进行。
- 当原暂停理由被新信息挑战、推翻，或被证明遗漏了足以改变结论的关键条件时，旧路线才更值得重新带回复审。

复审后的常见结果可以收敛为三类：恢复原路线、暂停且暂无当前路线、由用户确认正式换根。若新信息只是证明局部问题而未动摇路线前提，可以考虑恢复；否则尽量不要靠“再随便试试”绕过暂停。

正式换根时，通常让旧路线保留为历史，新路线进入当前路线状态；关键上下文保留根目标和跨阶段约束，移除旧路线的具体前提，避免历史获得默认优先级。

## 什么时候更新

普通讨论不必每轮输出完整树。形成重要决定、关闭顶层分支、切换主要分支、结构明显变化、对话过长或准备交接时，再生成完整 Snapshot。关闭顶层分支时，先尝试完成压缩归档；更新前可快速检查：树是否仍置顶、展示树是否纯净、当前节点和下一步是否清楚、活跃信息是否已从历史中抽出、历史索引能否定位归档、上下文是否过长、暂定是否被误写成已验证、以及新节点是否真的是规则缺口。

当用户要求导出或跨会话继续时，根据最近 Snapshot 与之后的正式变化生成完整 `TODO.md`；不要凭聊天记忆重构。

## 版本定位

这是当前正式版。它把路线复审、暂停和干净展示树作为优先考虑的方向，但不要求每个任务机械套用同一套触发数量或状态迁移；遇到新任务时仍应结合上下文判断是否适用。
