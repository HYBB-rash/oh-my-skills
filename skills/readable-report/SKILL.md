# 可读报告

让读者理解结论、理由与适用条件。保留原报告，另存阅读版；不追加调研，不把不确定性改成定论。关键限制随结论出现，完整输入和来源保留在详情入口。用户指定的格式、风格优先；短文或纯文字改写可直接交付 Markdown。

## 默认生产入口

默认用用户选定的 **Luna / medium** 单生产者完成新稿、机器检查、三项内容审读和两张图审读。使用时简短说明这一路由。在支持明确模型选择的子代理工具中，以 `gpt-5.6-luna`、`medium`、新上下文派发一次，把本 Skill 路径、原文、输出目录和用户要求交给它；已经是该生产者就直接执行，禁止递归派发。父任务只交付成品与真实状态，不重复语义审查。不修改主任务型号，不创建用户侧新任务；能力缺失则明确记录实际型号/未完成步骤，不冒充已采用 Luna 或已通过检查。

默认 HTML 使用脚本内嵌的安静阅读样式：问题导航、连续的完整解释，以及仅在原文支持时出现的条件比较。模型负责解释内容，稳定装配与检查由脚本负责。先准备 UTF-8 原文快照（其他格式先读取/提取并保留原文件），一次初始化新工作目录（把 `<skill-dir>` 替换为本 Skill 的实际安装目录）：

```sh
python3 "<skill-dir>/scripts/report.py" init 原报告.md --work 输出目录 --producer-model 实际型号 --producer-effort 实际档位 --producer-evidence 实际派发依据
```

之后固定工具的工作目录为返回的 `working_directory`，只用短命令：

1. `./rr context`：返回当前原文与按需编辑协议；照它写 `draft.json`。
2. `./rr submit`：先保存原稿字节，再装配独立 `report.html` 并执行固定检查；按返回清单审读内容、实际查看两张本地图。
3. 把审读表写入 `verdict.json`，`./rr finish` 留档；`./rr status` 查看成品与收据。

执行失败用 `./rr retry`，复用已保存内容，仅继续失败步骤。审读表被拒绝时保留失败提交，只修该表再 `./rr finish`；不得为了重试重新生成全文、放宽引用校验或手改检查证据。需要实质改稿时新建工作目录，旧稿和失败记录保留。

## 结果口径

固定机器检查需要已有 Python、Node（支持内置 WebSocket）和 Chrome；用独立临时浏览器与动态本地端口，不依赖现有标签页。每步 4 秒、总检查预算 25 秒、自动重试 0；缺工具记未完成，不自行安装。环境确需指定已有程序时可用 `REPORT_NODE_BIN`、`REPORT_CHROME_BIN`。

`passed_in_scope` 只代表三项内容自查与两张第一解释节截图在清单范围内通过；不代表全文视觉审完、外部事实核验或用户验收。PDF 仅导出，未逐页视觉验收。实际缺陷记 `failed`，工具缺失或未审读记 `incomplete`；尚待审读也不能说通过。聊天只给成品链接、实际状态和影响使用的限制，用可用预览工具打开成品。指定其他格式或风格时沿用内容原则，如实说明实际做过的检查，不套用默认 HTML 的通过记录。
